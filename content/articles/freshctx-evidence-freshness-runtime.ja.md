AIエージェントの失敗には、これまで「ハルシネーション」で一括りにされてきたのとは別の型があります。推論は論理的に正しく、ツールも仕様どおり動いた。それなのにアクションが間違う。原因は、推論してから実行するまでの間に現実が変わったこと。この「証拠の鮮度」を実行直前に再検証するオープンソースが、2026年8月28日に公開されました。名前はFreshCtxです。

なお当社（株式会社TOE／AIの鬼）は、AI導入支援・AI検索対策を売りうる立場です。以下、素材と当社の実測に書いてあることだけを、盛らずに整理します。

## 「ハルシネーションではない失敗」とは何か

[Zenn AI](https://zenn.dev/freshctx_dev/articles/b214bb81fc75d4)に公開された記事が指摘するのは、次の失敗パターンです。モデルはハルシネーションを起こしていない。推論にも明らかな誤りはない。ツールも仕様どおりに動作した。それでも、最終的なアクションが間違ってしまう。

記事はこれを時系列で示しています。

| 時刻 | 起きたこと |
| --- | --- |
| 10:00 | エージェントがシステム状態を観測 |
| 10:01 | その証拠をもとに推論 |
| 10:05 | 元の証拠が変化 |
| 10:15 | 以前の判断を実行 |

10:01時点では完全に正しかった推論が、10:15には使えなくなっている。推論が論理的に間違ったのではなく、古くなった（stale）のです。記事はこれを「ハルシネーションの問題ではなく、実行時の証拠鮮度（evidence freshness）の問題」と切り分けています。

## 具体例：在庫が実行前に減っていた

素材が挙げる例はシンプルです。注文処理を担当するエージェントが、在庫12・注文数10を確認し「この注文は処理できる」と判断する。この推論自体は正しい。しかし実行前に別の取引が8個を消費し、在庫は4になる。古い推論がそのまま残っていれば、エージェントは誤ったアクションを実行しうる、という流れです。

ここが中小企業にとって効いてきます。ハルシネーションなら「モデルが優秀になれば解決する」という道筋が見えます。ところがこの鮮度問題は、モデルの性能とは無関係だと素材は述べています。最強のAIを使っていても、古い証拠に基づく推論なら実行時に破綻しうる。つまりエージェント型のAI活用が増えるほど避けられなくなる、という主張です。日本の製造業で在庫管理や機械稼働状況の自動判断をAIに任せる場合、この論点は先読みしておく値打ちがあります。

## FreshCtxが再検証するもの・しないもの

FreshCtxは、再検証を「第一級ランタイムプリミティブ」として組み込む設計だと説明されています。エージェントは推論が依存した証拠を宣言し、AIによるアクションを実行する前に、FreshCtxがその証拠を再検証する。現在のランタイムは4つの状態を区別します。

| 状態 | 意味（素材の記述） |
| --- | --- |
| FRESH | 証拠は今も有効 |
| CHANGED | 証拠が変化した |
| EXPIRED | 証拠が失効した |
| UNAVAILABLE | 証拠を検証できない |

証拠が変化・失効した、または検証できない場合、ランタイムポリシーは古い推論が黙って実行に進むことを防げる、とされています。v0.1が再検証できる証拠ソースは、ファイルシステム／Gitの状態／HTTPリソース／PostgreSQLデータソース／MCPで読み取り可能なリソースの5つ。アダプターは拡張可能です。PythonのオープンソースでPyPIから`pip install freshctx`で導入できる、とも書かれています。

素材は「しないこと」も明示しています。FreshCtxはMemoryでもRAGでも認可でもない。Memoryが答えるのは「以前何を観測したか」であって、その内容が今も真かは別問題。RAGは検索の後に起きる証拠変化を防げない。認可が問うのは「実行してよいか」であって「証拠がまだ有効か」ではない。十分な権限を持つエージェントでも、古い推論で誤ったアクションを実行できる、という整理です。あえて狭いランタイムに絞り、既存のエージェントスタックを置き換えずに鮮度制御を追加できることを重視した、と述べています。

## 中小企業の自動判断で何が変わるのか

当社は社内業務の自動化を27本運用しており、この記事を含むサイトの収集・要約・記事化も人手を介さず毎日自動で回しています（2026-08-31時点で収集済みニュース3000件／自社要約つき1876件／本文取得済み957件／記事273本、運用中のAI API課金は0円）。この自動運用の実感から言えるのは、「観測→推論→実行」の間に時間が空くほど、証拠のズレが入り込む余地が増えるということです。素材の言う在庫ドリフトは、まさに時間軸の問題です。

ただし、FreshCtxを入れれば誤判断がどれだけ減るのか、当社は測っていません。導入も検証もしていないので、効果は分かりません。素材が主張する「モデル性能と無関係」という点も、当社の実測で裏づけたものではなく、あくまでZenn AIの記事の主張です。

## この記事で言えないこと

- FreshCtxを本番導入した効果（誤判断の減少率など）。当社は導入も検証もしておらず、測っていません。
- 「モデル性能と無関係に鮮度問題は残る」という主張の妥当性。これはZenn AIの記事の主張で、当社が実測で確かめたものではありません。
- FreshCtx以外の同種ツールとの比較。素材に他社の同一報道は0件で、比較材料がありません。
- 導入の手間・運用コスト・日本語環境での挙動。素材からは分かりません。
- 在庫12→注文10の例は素材が挙げた説明用の例であり、実在企業の事例ではありません。

## まとめ

- 素材が指摘するのは、推論もツールも正しいのにアクションが間違う「証拠鮮度」の失敗で、ハルシネーションとは別の型です。
- FreshCtxは実行直前に、宣言された証拠（ファイル・Git・HTTP・PostgreSQL・MCP読み取り資源）を再検証し、FRESH/CHANGED/EXPIRED/UNAVAILABLEの4状態で古い推論の実行を止められる設計です。
- これはMemory・RAG・認可のいずれとも別問題だと素材は切り分けています。
- 中小企業で在庫や機械稼働の自動判断をAIに任せるなら、「実行直前に証拠を再検証する」という概念は先読みする値打ちがありますが、その効果を当社は測っていません。
- 当社はサイト運用を毎日自動で回していますが（API課金0円）、FreshCtxの導入・検証はしておらず、効果は分かりません。
